# C review 저장 구현 현황

기준 develop: `865fd4e`. 현재 구현은 C 담당 이슈 #39의 일부이며, 전체 review 저장 API가 완료된 상태는 아니다.

## 원본 확인 함수

`review_sources.open_review_source(project_id, session, root, source_ref)`는 검증한 `ViewerSource`와 표시 변환 기록의 쌍을 반환한다. 프로젝트, 세션과 저장 루트는 앱이 제공한다. 요청 본문의 값으로 인증 범위나 저장 경로를 바꾸지 않는다.

- DICOM은 기존 `open_dicom_display`를 사용한다. 저장된 환자, 검사, 시리즈와 객체의 관계를 검사하고 실제 보관 원본을 다시 읽어 B 해석기로 확인한다. 두 번째 반환값은 실제 해석 결과의 `provenance()`다.
- PNG와 JPEG는 기존 `open_selected_original`을 사용한다. 두 번째 반환값은 `None`이다.
- 두 경로 모두 요청한 해시, 실제 바이트 해시, 형식과 방향 보정 후 크기를 대조한다.
- 현재 지원 프레임은 정수 `0` 하나다. 논리형과 실수는 프레임이나 픽셀 크기로 받지 않는다.
- 알 수 없는 참조 schema, 누락 필드와 추가 경로 필드를 거절한다. 파일명이나 사용자 지정 URL로 원본을 열지 않는다.
- 함수는 조회만 수행하며 원본, 결과 파일과 DB를 쓰거나 삭제하지 않는다.

입력과 원본 불일치는 `ReviewSourceError.code`로 구분한다. 주요 코드는 `invalid_input`, `source_mismatch`, `unsupported_frame`, `original_unavailable`이다. 기존 PNG/JPEG 서비스의 `FirebaseRequestError`는 HTTP 상태를 보존한다. DICOM 서비스의 `DicomOpenError`는 `permission_denied`, `session_expired`, `remote_failure` 등으로 전달한다. 상위 review API는 이 두 기존 오류 경계를 SaveResult와 LoadResult에 맞게 변환해야 한다.

## 처리 환경 정보

`ProcessingRecord.environment`는 선택적인 키워드 전용 필드다. 기존 위치 인수를 유지하며 기본값은 `None`이다. 값이 있으면 처리 JSON의 최상위에 보존한다. 과거 기록에 필드가 없거나 `null`이면 `None`으로 읽고 현재 실행 환경으로 대체하지 않는다. 요청 고정 시 중첩 사전까지 깊은 복사한다.

## 처리 결과 파일

`review_storage.save_processing_result(root, session, source, processing)`는 실제 결과 RGB 이미지를 PNG로 보관하고 처리 메타데이터를 반환한다. `load_processing_result(root, session, source, metadata)`는 파일 해시와 원본 크기를 검사한 뒤 `ProcessingRecord`를 복원한다. 두 함수는 review의 DB 저장 완료를 뜻하지 않는 파일 계층 함수다.

호출 서비스가 먼저 `open_review_source`로 인증 범위와 원본 연결을 확인해야 한다. 새 처리의 알고리즘 지원 여부와 실제 적용 여부도 상위 서비스에서 확인해야 한다. 이 파일 함수만 호출해 원본 연결과 적용 검사를 대체하지 않는다.

결과는 기존 PNG/JPEG 케이스와 같은 내부 `root/results` 아래 사용자별 해시 경로에 둔다. 원본 DICOM을 표시용 PNG로 바꾸지 않는다. PNG 바이트의 SHA-256은 `result_key`, 원본 바이트의 SHA-256은 `source_id`로 구분한다. 같은 결과를 다시 보관해도 기존 결과를 덮어쓰지 않는다.

직렬화한 메타데이터는 UTF-8 인코딩 60,000바이트 이하인지 파일 쓰기 전에 확인한다. 이 검사는 처리 부분의 검사이며 최종 review 전체 스냅샷에도 같은 상한을 적용해야 한다. 설정과 결과를 먼저 복사하므로 이후 화면 편집이 반환한 기록과 파일에 섞이지 않는다.

처리가 `None`이면 메타데이터도 `None`이고 결과 파일을 만들지 않는다. 재열기는 알고리즘을 자동 실행하지 않으며 과거 환경 정보가 없거나 과거 알고리즘인 기록도 저장 결과 자체를 읽는다. 파일 계층은 기존 통계 형식을 검사하고, 아래 초안 검증은 실제 픽셀에서 통계 수치를 다시 계산해 대조한다.

## 저장 전 초안 검증

`review_validation.prepare_review_draft(project_id, session, root, draft)`는 실제 원본과 확인한 초안의 쌍을 반환한다. 이 함수도 파일이나 DB를 쓰지 않는다. 새 review 서비스는 이 검증 뒤 결과 파일을 보관하고 DB 저장을 수행해야 한다.

- 전체 초안의 schema, ID와 필수 필드를 확인한다. 누락 필드를 이전 저장값으로 채우지 않는다.
- 실제 원본을 다시 열어 SourceRef를 검사하고, B 해석기가 반환한 provenance와 요청의 display_mapping을 대조한다. PNG/JPEG는 null이어야 한다.
- ROI가 있으면 원본과 실제 결과에서 기존 compare_roi를 다시 호출한다. 픽셀 수, 평균과 모집단 분산, 계산 정의와 좌표를 대조한다. 수치 오차 허용값은 상대 오차 1e-12와 절대 오차 1e-9다. 음수, NaN과 무한대는 허용하지 않는다.
- ROI와 처리가 각각 없는 경우를 구분한다. 처리가 없으면 결과 통계는 null이고, ROI가 없으면 전체 통계는 null이다. 처리 기록 안의 ROI와 통계도 전체 초안과 일치해야 한다.
- 실제 적용 설정과 결과 이미지를 복사해 반환한다. 이후 화면의 설정, 통계와 픽셀 편집은 고정한 사본에 반영되지 않는다.
- 결과 파일의 고정 길이 참조를 포함한 전체 초안이 UTF-8 60,000바이트 이하인지 검사한다. DB 저장 직전 최종 스냅샷에도 상한을 다시 적용해야 한다.

현재 주석 목록이 있는 초안은 B 측정 재검증 미연결을 이유로 거절한다. 주석을 버리고 빈 목록으로 저장하지 않는다. 새 알고리즘의 지원 판정과 과거 미지원 처리의 불변 참조 유지도 상위 서비스 연결이 남아 있다. 이 준비 함수를 전체 저장 API나 알고리즘 재현 검증으로 설명하지 않는다.

## DB commit 전송 및 재시도 확인

`review_commit_transport.commit_review`는 검증과 직렬화를 마친 스냅샷을 받아 최신 헤드와 불변 버전을 하나의 Firestore commit으로 전송한다. 이 함수는 저수준 전송 계층이다. 원본과 입력 승인, 버전 번호의 신뢰성은 호출할 저장 서비스가 먼저 확인해야 한다.

응답 오류 뒤 같은 작업 이력이 있으면 요청 해시, 직렬화된 내용과 버전 번호를 대조한다. 모두 일치할 때만 기존 스냅샷을 반환한다. 이력이 없으면 최신 헤드의 실제 변경 여부를 확인하며, 최신 버전도 같으면 원래 오류를 유지한다. 재조회 실패는 성공이나 충돌로 바꾸지 않는다. 쓰기 성공 뒤 이력 조회에 실패할 수도 있으므로 상위 서비스는 같은 고정 요청의 재시도를 제공해야 한다.

임시 모의 Firestore 시험으로 중복 전송, 응답 유실, 두 작성자의 충돌, 권한 오류, 잘못된 이력을 검사했다. 실제 Firestore 규칙은 아직 이 경로를 허용하도록 작성하거나 배포하지 않았다.

## 주석 검증 준비

`review_annotations.validate_annotations`는 주석 ID, 원본 참조, 선과 사각형 좌표, 중복 여부와 필드 구성을 검사한다. 신뢰된 원본 메타데이터로 받은 B 보정 및 측정 함수의 계산 결과와 요청값도 비교한다. 테스트는 고정된 계산 어댑터를 사용한다.

이 함수는 아직 실제 저장 경로에 연결되지 않았다. 운영 경로는 사용자 입력을 함수나 메타데이터로 신뢰해서는 안 되며, 실제 원본에서 읽은 메타데이터와 실제 B 함수를 연결해야 한다. 따라서 주석 저장과 이력 보존 전체는 미완료다.

## 재시도 요청 보존

`review_pending.remember_review`는 이미 검증하고 직렬화한 스냅샷, 기준 버전과 작업 ID를 사용자 및 프로젝트 범위의 SQLite에 보관한다. 같은 작업 ID의 다른 요청은 거절한다. `get_pending_review`는 저장 형식을 다시 검증해 새 프로세스에서도 동일한 요청을 읽는다.

`review_retry.retry_review`는 보관된 요청의 원본과 결과를 다시 열고 ROI 통계와 초안을 검증한 뒤 동일 작업 ID로 DB에 전송한다. 실패나 성공 모두 재시도 기록을 유지한다. 이 함수는 내부 구성 요소이며, 최초 저장 흐름과 화면, B 알고리즘 검증 및 성공 확인 후 기록 정리 절차는 아직 연결되지 않았다. 따라서 파일 저장 실패 복구와 재시도 전체를 완료로 표시하지 않는다.

## 구현 체크리스트

- [x] 기존 DICOM과 PNG/JPEG 원본 재열기 서비스에 SourceRef 검증을 연결했다.
- [x] 다른 소유자와 프로젝트, 원본 해시, 크기, 환자와 시리즈 불일치를 거절한다.
- [x] 실제 DICOM, PNG와 JPEG 파일로 임시 저장소를 읽고 모의 HTTP 경계에서 검사한다.
- [x] 과거 environment 누락, 저장과 복원 및 요청 고정의 호환성을 검사한다.
- [x] DICOM 원본을 변경하지 않고 실제 결과를 별도 PNG로 보관하고 읽는다.
- [x] 결과의 픽셀, 설정, ROI와 환경을 복원하고 파일 유실, 변조와 크기 불일치를 거절한다.
- [x] UTF-8 메타데이터 상한과 동일 결과 파일 재사용을 검사한다.
- [x] 실제 원본과 결과에서 ROI 통계를 다시 계산해 위조된 수치와 표시 변환을 거절한다.
- [x] 전체 초안과 처리 기록의 ROI 일치, 처리 없는 ROI와 ROI 없는 처리를 검사한다.
- [x] 모의 DB에서 원자적 헤드와 이력 쓰기, 중복 재시도와 버전 충돌을 검사한다.
- [x] 모의 DB에서 재조회 실패와 근거 없는 권한 오류를 성공이나 충돌로 바꾸지 않는다.
- [ ] C02 전체: save_review, load_review와 list_review_versions에 연결한다.
- [ ] 결과 파일을 review 스냅샷과 연결하고 불변 버전 및 고정 재시도 요청을 저장한다.
- [ ] B 측정 재검증과 A 화면 연결을 완료한다.
- [ ] 실제 Firebase 권한과 Linux 실행을 확인한다.

원본 참조, 결과 파일과 초안 검증을 구현한 단계이므로 새 review의 DB 저장, 변경 이력과 앱 재실행 복원이 완료됐다고 표시하지 않는다. 시험은 임시 원본 파일과 모의 DB를 사용하며 실서버 규칙 배포를 검증한 결과가 아니다.
