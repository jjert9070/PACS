# B와 C 통합 수동 검증 체크리스트

대상 브랜치: `intergrationOfBC`. 작성일: 2026년 11월 17일.
아래 체크는 현재 통합본에서 직접 확인한 뒤 표시한다. 기존 C 단독 검증 사진으로
새 BC 연결의 검증까지 완료한 것으로 표시하지 않는다.

2026년 11월 17일 기준 기본 13개 항목 중 7개를 실제 브라우저에서 확인했다.
완료 항목은 1, 2, 4, 5, 6, 7, 8이며 자동 테스트 통과와 구분한다.
사진은 [PR 검증 기록](bc-integration-pr.md)에서 확인한다. 중간에 제목을 바꿔 저장한
이력이 있으므로 실제 메모 변경은 v3, 강도 3.0 재처리는 v4에 기록됐다.

## 준비

- 앱을 최신 로컬 코드로 다시 실행하고 로그인한다. Git pull은 이 절차에 포함하지 않는다.
- 기존 테스트 케이스와 구분해 새 제목 `BC 수동 검증 001`을 사용한다.
- **합성 예시**를 사용한다. 원본은 640 × 480 픽셀이다.
- 가우시안 강도는 2.0, ROI는 left 12, top 0, right 480, bottom 445로 시작한다.
- 저장 성공 후 계속 수정할 때는 먼저 **저장본 다시 열기**를 누른다.
- 케이스 ID, 영상 ID, 버전, 실제 적용값과 ROI 통계를 기록한다. 처리 기록이 없는
  과거 케이스의 설정과 결과는 이번 수정으로 자동 생성되지 않는다.

## 먼저 확인할 항목

- [x] **1. 처리 결과와 ROI를 함께 저장한다.**
  가우시안 적용과 ROI 적용을 각각 누른다. 제목 `BC 수동 검증 001`, 메모
  `첫 번째 메모`, 출처 `앱의 합성 예시`로 원본과 케이스를 저장한다.
  통과 기준: 원본과 결과 모두 같은 위치에 노란 테두리가 보이고, 양쪽 ROI 픽셀 수는
  208,260이다. 저장 성공이 표시된다. 저장본을 다시 열면 목록에 v1이 표시된다.

- [x] **2. 새로고침과 재로그인 후 같은 케이스를 다시 연다.**
  내 케이스 목록을 불러와 기록해 둔 케이스 ID로 연다.
  통과 기준: 원본과 결과, 제목과 메모, 출처가 복원된다. 가우시안 입력은 2.0,
  ROI 입력 네 칸과 통계는 저장 전 값과 같다. 케이스 ID와 영상 ID, 버전도 같다.
  재열기만으로 새 버전이 생기지 않는다. 기본값과 Session State를 중복 지정했다는
  영문 경고가 없고, **처리 기록 상세**는 접혀 있으며 펼치면 저장된 설정과 통계가 보인다.

- [ ] **3. 확대와 이동이 처리 기록을 바꾸지 않는다.**
  확대 배율을 2배로 바꾸고 가로와 세로 위치를 조절한 뒤 보기 초기화를 누른다.
  통과 기준: 두 영상의 표시 위치와 배율이 함께 바뀐다. ROI 통계와 적용값,
  영상 ID와 저장 버전은 그대로다. 일부 ROI 테두리가 화면 밖으로 나가는 것은 정상이다.

- [x] **4. 적용하지 않은 설정은 저장되지 않는다.**
  강도 입력만 3.0으로 바꾸고 가우시안 적용은 누르지 않는다. 메모를 `두 번째 메모`로
  바꿔 저장하고 저장본을 다시 연다.
  통과 기준: v2가 되고 메모는 바뀌지만 실제 설정과 복원 입력은 2.0이다.
  결과와 ROI 통계는 v1과 같다. 변경 이력에서 v1과 v2의 메모를 각각 확인할 수 있다.

- [x] **5. 다시 처리하면 새 결과를 저장하고 이전 버전은 보존한다.**
  복원된 케이스에서 강도를 3.0으로 바꾸고 가우시안 적용 후 저장한다. 다시 연다.
  통과 기준: v3의 설정과 결과가 3.0 적용 상태로 복원된다. 변경 이력을 펼치면
  v1과 v2에는 2.0 설정과 기존 ROI 통계, 결과 참조가 남아 있다.
  과거 버전을 펼쳐 읽는 것과 현재 편집 화면으로 복원하는 것은 별개다.

- [x] **6. ROI 변경과 해제를 저장할 수 있다.**
  ROI를 (0, 0, 400, 200)으로 적용하고 저장한 뒤 다시 연다.
  통과 기준: 입력 좌표와 테두리, 양쪽 픽셀 수 80,000이 복원된다.
  이어 ROI 해제 후 저장하고 다시 열면 테두리와 선택 ROI가 없고 결과 영상은 남아 있다.
  ROI 입력란의 기본값은 선택된 ROI를 뜻하지 않는다. 이전 버전의 ROI 기록도 확인한다.

- [x] **7. 처리 결과만 바꿔도 폐기 확인 없이 전환되지 않는다.**
  저장본을 연 뒤 메모는 그대로 두고 강도를 4.0으로 적용한다. 저장하지 않고
  새 케이스 작성을 누른다.
  통과 기준: 저장 전 변경 경고가 나타나고 기존 케이스와 새 결과가 유지된다.
  폐기 확인을 체크한 뒤 다시 누르면 새 케이스가 되고 제목, 메모와 출처가 비워진다.
  같은 시험을 ROI 변경만 한 경우와 ROI 해제만 한 경우에도 반복한다.

- [x] **8. 같은 원본을 쓰는 다른 케이스의 설정이 섞이지 않는다.**
  같은 합성 예시로 `BC 수동 검증 002`를 만들되 강도 1.0과 다른 ROI를 저장한다.
  001과 002를 번갈아 연다. 저장 전 변경이 있으면 폐기 확인 후 전환한다.
  통과 기준: 영상 ID는 같아도 케이스 ID는 다르다. 각 케이스의 적용값과 ROI,
  결과와 메모가 각자의 저장 내용으로 복원된다. **통계와 저장 상세뿐 아니라 왼쪽
  입력란까지** 비교한다. 001은 강도 3.0과 전체 ROI, 002는 강도 1.0과
  (20, 20, 100, 100)의 ROI로 준비하면 구분하기 쉽다. 각각의 마지막 저장값을
  기준으로 비교하며 ROI가 없는 케이스는 미선택 안내가 유지되어야 한다.

- [ ] **9. 감마와 임계값도 같은 저장 흐름으로 동작한다.**
  각각 새 케이스를 만들어 감마 0.5, 임계값 128을 적용한다. ROI를 적용하고 저장한
  뒤 새로고침과 재로그인 후 다시 연다.
  통과 기준: 선택 알고리즘과 입력값, 결과 영상과 ROI 통계가 각각 복원된다.
  감마 결과는 밝아지고 임계값 결과는 흑백이다. 재열기 후 다른 알고리즘을 선택해
  적용하면 새 결과로 바뀌며, 저장 후 이전 버전에는 기존 알고리즘 기록이 남는다.

- [ ] **10. 잘못된 ROI를 저장하지 않고 정상 입력으로 복구한다.**
  저장본을 연 뒤 left 400, right 10처럼 거꾸로 된 ROI를 적용한다.
  통과 기준: 오류가 표시되고 저장 버튼이 비활성화된다. 이전 통계를 새 ROI의
  통계처럼 표시하지 않는다. 올바른 ROI를 적용하거나 ROI 해제를 누르면 복구된다.

## 실제 환경에서 추가 확인할 항목

- [ ] **11. 두 창의 처리 결과 저장 충돌을 막는다.**
  일반 창과 시크릿 창에서 같은 계정으로 같은 케이스의 같은 버전을 연다.
  일반 창에서는 강도 4.0과 메모 `창 A`, 시크릿 창에서는 강도 5.0과 메모 `창 B`를
  각각 적용한다. A를 먼저 저장하고 B를 저장한다. 동시에 클릭할 필요는 없다.
  통과 기준: B는 다른 창의 선행 저장 안내를 받고 입력을 유지한다. B의 입력을
  따로 기록한 뒤 폐기 확인 후 다시 열면 A의 설정과 메모가 나온다. B의 실패로
  추가 버전이 생기지 않는다. 터미널에서 `reason=stale_case_version`도 확인한다.

- [ ] **12. 서버를 재시작한 뒤에도 재열기된다.**
  저장을 마친 뒤 앱 서버를 종료하고 기존 실행 명령으로 다시 실행한다. 로그인 후
  같은 케이스를 연다. 통과 기준: 케이스 ID와 영상 ID, 적용값과 ROI, 결과가 같다.
  이 시험은 현재 PC의 로컬 저장 지속성을 확인하며 JCloud 영구 보존 시험은 아니다.

- [ ] **13. 로그아웃과 계정 전환 후 화면이 정리된다.**
  처리 결과가 보이는 상태에서 로그아웃한다. 다른 테스트 계정이 준비되면 그 계정으로
  로그인해 목록을 불러온다. 통과 기준: 로그아웃 직후에는 로그인 화면만 보이고,
  다른 계정에서는 첫 계정의 케이스와 영상, 임시 입력이 보이지 않는다.

## 조건이 마련되면 별도로 확인

- [ ] **실패한 저장의 동일 요청 재시도.** 실패 상태에서 재시도 버튼이 나타난 경우
  요청 ID를 기록한다. 입력을 바꾸어도 재시도는 최초 제출 내용과 같은 요청 ID를
  사용해야 한다. 성공했다면 해당 최초 내용만 저장되고 중복 버전이 없어야 한다.
  원인이 남아 있는 권한 거절이나 버전 충돌은 재시도도 실패하는 것이 정상이다.
  브라우저만 오프라인으로 바꾸어서는 서버의 Firestore 실패를 재현할 수 없다.
- [ ] **다른 UID 경로와 비로그인 요청의 서버 거절.** 목록에 다른 계정 자료가
  안 보이는 것만으로 이 항목을 완료 처리하지 않는다. 실제 요청 또는 보안 규칙
  시험이 필요하며, 이번 자동 시험의 모의 응답으로 실제 배포 규칙까지 증명하지 않는다.

## 증빙 기록

각 시험에서 케이스 ID, 저장 전후 버전, 실제 적용값과 ROI 좌표, 기대 결과와 실제
결과를 함께 남긴다. 정상 결과는 저장 전과 재열기 후 화면을 한 쌍으로, 충돌은
두 창의 결과와 이유 로그를 함께 남기면 비교하기 쉽다.

## 자동 확인과 수동 확인의 경계

자동 시험은 실제 B 알고리즘, Streamlit AppTest, 임시 파일 저장과 모의 Firestore를
사용한다. 저장 당시 이미지와 설정의 보존, 재열기 중 알고리즘 재실행 방지,
처리 실패 후 복구, 재시도 입력 고정과 충돌 시 선행 저장 보존을 확인한다.
실제 로그인과 배포된 보안 규칙, 브라우저 표시와 실제 서버 재시작은 위 수동 항목으로
확인한다. 검토자 배정과 역할별 상태 전이는 현재 구현 범위에서 제외한다.
